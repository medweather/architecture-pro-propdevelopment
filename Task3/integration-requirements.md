# Требования к внешним интеграциям — Умный дом

## 1. Требования к безопасности

### 1.1 Транспортная безопасность

- Все внешние вызовы выполняются исключительно по **TLS 1.2 / 1.3** (HTTPS).
- Сертификаты проверяются двухсторонне (mTLS — опционально для webhook, см. п. 2.2).
- Запрещена передача данных по незащищённым каналам. HTTP-запросы должны
  безусловно отклоняться.

### 1.2 Безопасность webhook-эндпоинтов

- Webhook-запросы от Партнёра в PropDevelopment должны содержать подпись
  (HMAC-SHA256) тела запроса. Подпись передаётся в заголовке
  `X-Signature-256`.
- PropDevelopment проверяет подпись секретным ключом, известным обеим сторонам.
- В дополнение к подписи может применяться **белый список IP-адресов** Партнёра
  на уровне файрвола или API-шлюза.
- Webhook-эндпоинты отдают HTTP `200 OK` только при успешной валидации.
  При ошибке подписи — `401 Unauthorized`.

### 1.3 Rate Limiting

- PropDevelopment устанавливает лимиты на количество вызовов к API Партнёра.
- Партнёр обязан поддерживать механизм `Retry-After` при превышении лимита.
- Для webhook-уведомлений Партнёр должен реализовать экспоненциальную
  задержку повторной отправки при недоступности эндпоинта PropDevelopment.

### 1.4 Аудит и логирование

- Все входящие и исходящие интеграционные запросы логируются в централизованную
  систему аудита PropDevelopment.
- Лог содержит: timestamp, источник/цель, тип запроса, статус ответа,
  идентификатор корреляции.
- Длительность хранения логов — не менее 1 года.

### 1.5 Защита данных

- Данные реестров жильцов и авто (биометрия, персональные данные) передаются
  в **зашифрованном виде** (использование полей подписанных JWT или payload
  encryption на уровне приложения).
- Стороны обязуются соблюдать требования 152-ФЗ «О персональных данных» при
  обработке биометрических данных и номерных знаков.

## 2. Протоколы аутентификации и авторизации

### 2.1 REST API (PropDevelopment → Партнёр)

**Аутентификация:** OAuth 2.0 Client Credentials Grant.

- PropDevelopment (клиент) получает **Client ID** и **Client Secret** от Партнёра.
- При каждом вызове API запрашивается **access token** у Партнёра
  (endpoint: `POST /oauth/token`).
- Token передаётся в заголовке `Authorization: Bearer <token>`.
- Token имеет ограниченное время жизни (TTL, не более 15 минут).
- По истечении TTL клиент получает новый token.

**Авторизация:** scoped-доступ.

- Партнёр выделяет отдельные scope для каждого сервиса:
  - `intercom:write` — управление домофоном (реестр лиц, команды открытия).
  - `barrier:write` — управление шлагбаумом (реестр авто, команды открытия).
- PropDevelopment использует минимально необходимый набор scope.

### 2.2 Webhook (Партнёр → PropDevelopment)

**Аутентификация:** базируется на HMAC-подписи (см. п. 2.2).

- Секретный ключ (shared secret) распространяется при настройке интеграции
  через защищённый канал вне полосы (out-of-band).
- Партнёр вычисляет подпись от тела запроса и передаёт её в заголовке.
- PropDevelopment валидирует подпись.
- **Опционально:** mTLS — двухстороннее подтверждение сертификатов на уровне
  транспорта. Рекомендуется, если Партнёр поддерживает.

**Авторизация:** webhook-запросы не требуют дополнительной авторизации —
аутентификация через подпись является достаточной. Тип события
(intercom / barrier) определяется полем `event_type` в теле запроса, и
PropDevelopment применяет внутренние правила доступа к данным.

## 3. Взаимодействие между системами предприятия и внешней платформой

### 3.1 Взаимодействие REST API

**Outbound (PropDevelopment → Партнёр):**

| Операция | Метод | Путь | Тело запроса |
|---|---|---|---|
| Синхронизация реестра жильцов | `PUT` | `/api/v1/intercom/residents` | `{ "residents": [...], "building_id": "..." }` |
| Команда открыть дверь | `POST` | `/api/v1/intercom/open` | `{ "door_id": "...", "requester": "..." }` |
| Синхронизация реестра авто | `PUT` | `/api/v1/barrier/vehicles` | `{ "vehicles": [...], "barrier_id": "..." }` |
| Команда открыть шлагбаум | `POST` | `/api/v1/barrier/open` | `{ "barrier_id": "...", "requester": "..." }` |

- Все ответы содержат идентификатор корреляции в заголовке `X-Request-ID`.
- Коды ответа: `200 OK` — успех, `202 Accepted` — команда принята, `4xx/5xx` — ошибка.
- При ошибках тело ответа содержит JSON: `{ "error": "...", "code": "..." }`.

### 3.2 Взаимодействие Webhook

**Inbound (Партнёр → PropDevelopment):**

| Событие | Тип | Данные |
|---|---|---|
| Вход по лицу | `intercom.entry` | `{ "face_id", "building_id", "timestamp", "granted" }` |
| Попытка входа (отказ) | `intercom.denied` | `{ "face_id", "building_id", "timestamp", "reason" }` |
| Выезд авто | `barrier.exit` | `{ "plate", "barrier_id", "timestamp" }` |
| Попытка проезда (отказ) | `barrier.denied` | `{ "plate", "barrier_id", "timestamp", "reason" }` |

- Webhook-запросы отправляются методом `POST` на зарегистрированный эндпоинт
  PropDevelopment.
- Партнёр ожидает HTTP `200 OK` как подтверждение получения.
- При отсутствии подтверждения Партнёр выполняет повторную отправку с
  экспоненциальной задержкой (3 попытки, интервалы: 10с, 30с, 60с).
- Идемпотентность: каждое событие содержит уникальный `event_id`.
  PropDevelopment дедуплицирует по `event_id`.

### 3.3 Соглашение о формате данных

- Все данные передаются в формате **JSON** (кодировка UTF-8).
- Поля даты/времени — в формате **ISO 8601** (например, `2026-07-12T14:30:00Z`).
- Числовые идентификаторы передаются как строки.
- Имена полей — в `snake_case`.

### 3.4 SLA и отказоустойчивость

- Доступность API Партнёра — **99,9%**.
- Максимальное время ответа — **2 секунды** для синхронных REST-вызовов.
- Webhook-уведомления должны доставляться **не позднее 30 секунд** после
  наступления события.
- При недоступности Партнёра PropDevelopment кэширует команды на открытие
  (не более 5 мин) и повторяет отправку при восстановлении связи.
- Партнёр гарантирует обработку событий даже при временной недоступности
  эндпоинта PropDevelopment (буферизация, очередь).

## 4. Сценарии использования

### 4.1 Регистрация нового жильца

1. Собственник добавляет жильца в мобильном приложении.
2. PropDevelopment отправляет `PUT /api/v1/intercom/residents` с данными жильца
   (включая Face ID, если привязана биометрия).
3. Партнёр подтверждает синхронизацию.
4. При первой попытке жильца пройти — Партнёр распознаёт лицо, проверяет права
   через локальный реестр и открывает дверь.
5. Событие `intercom.entry` отправляется в PropDevelopment через webhook.

### 4.2 Удаление доступа

1. Собственник удаляет жильца/авто в приложении.
2. PropDevelopment отправляет `PUT /api/v1/intercom/residents` (или
   `PUT /api/v1/barrier/vehicles`) с обновлённым списком.
3. Партнёр обновляет локальный реестр.
4. При следующей попытке прохода — системе отказывает в доступе.

### 4.3 Экстренное открытие по звонку

1. Гость звонит в домофон.
2. Партнёр транслирует звонок на мобильное приложение собственника.
3. Собственник нажимает «Открыть».
4. PropDevelopment отправляет `POST /api/v1/intercom/open`.
5. Партнёр открывает дверь.
