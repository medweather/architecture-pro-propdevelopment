# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

### 1. Доступ к секретам
- **Кто**: `minikube-user` (пользователь с правами `system:masters`)
- **Где**: namespace `kube-system` — `kubectl get secrets -n kube-system` (HTTP 200 — успешно) и попытка доступа от имени `system:serviceaccount:secure-ops:monitoring` (HTTP 403 — отклонено RBAC)
- **Почему подозрительно**: Пользователь запросил список всех секретов в системном namespace `kube-system`, где хранятся токены, сертификаты и учётные данные компонентов кластера. Успешный ответ (HTTP 200) дал злоумышленнику информацию для дальнейшей атаки. Также была попытка доступа от имени сервисного аккаунта `monitoring` (HTTP 403 — отклонено RBAC). Это указывает на разведку (reconnaissance) с целью поиска учётных данных.

### 2. Привилегированные поды
- **Кто**: `minikube-user`
- **Комментарий**: Создан под `privileged-pod` с `securityContext.privileged: true`. Привилегированный под имеет полный доступ к хостовой системе, может монтировать `/proc`, запускать контейнеры в режиме ядра и потенциально скомпрометировать весь кластер. Это является прямой эскалацией привилегий.

### 3. Использование kubectl exec в чужом поде
- **Кто**: `minikube-user`
- **Что делал**: `kubectl exec -n secure-ops attacker-pod -- ls /` — выполнение команды внутри чужого контейнера `attacker-pod`. Позволяет читать данные, запускать процессы и потенциально перемещаться латерально по кластеру.

### 4. Создание RoleBinding с правами cluster-admin
- **Кто**: `minikube-user`
- **К чему привело**: Создан `RoleBinding` с именем `escalate-binding`, который связывает `ServiceAccount monitoring` с `ClusterRole cluster-admin`. Это даёт сервисному аккаунту полный контроль над кластером (HTTP 201 — создано успешно). Является критической эскалацией привилегий без согласования.

### 5. SelfSubjectAccessReview (проверка прав)
- **Кто**: `minikube-user`
- **Что делал**: `kubectl auth can-i get secrets --as=system:serviceaccount:secure-ops:monitoring` — злоумышленник проверяет, какие права доступа есть у сервисного аккаунта `monitoring`, прежде чем выполнять действия. Это классический разведывательный шаг.

### 6. Удаление audit-policy.yaml
- **Кто**: `minikube-user`
- **Комментарий**: Попытка удалить `configmap audit-policy` (HTTP 404 — ресурс не найден). Злоумышленник пытался отключить аудит, чтобы заметать следы. В продукции это привело бы к потере журналирования.

### 7. Ошибки политики RBAC
- Сервисный аккаунт `monitoring` в namespace `secure-ops` получил роль `cluster-admin` через `RoleBinding` — это нарушение принципа минимальных привилегий (least privilege). `RoleBinding` не был никем одобрен.
- Пользователь `minikube-user` входит в группу `system:masters`, что даёт ему неограниченный доступ. Административные действия такого пользователя должны быть ограничены временными токенами (just-in-time access).

## Вывод

Анализ audit.log выявил **7 типов подозрительных событий**, включая разведку (`auth can-i`, `get secrets`), эскалацию привилегий (`privileged-pod`, `cluster-admin RoleBinding`) и попытку сокрытия следов (удаление audit policy). Кластер был скомпрометирован:

1. Злоумышленник создал привилегированный под для выполнения команд с правами ядра.
2. Сервисный аккаунт `monitoring` через `RoleBinding escalate-binding` получил полный доступ `cluster-admin` **без согласования**.
3. Политика RBAC не использует принцип минимальных привилегий — `cluster-admin` назначен напрямую сервисному аккаунту в неймспейсе.

**Рекомендации:**
- Запретить создание привилегированных подов через `PodSecurity Admission` или `OPA Gatekeeper`.
- Внедрить approval workflow для RoleBinding с правами `cluster-admin`.
- Настроить оповещения по событиям `selfsubjectaccessreview` и `exec` в систему мониторинга.
- Использовать временные (JIT) токены для администраторов вместо постоянной группы `system:masters`.
